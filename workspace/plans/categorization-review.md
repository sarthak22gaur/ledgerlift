# Categorization review

Status: implemented and verified.

## Goal and decisions

Add **Review → Categorization** at `/review/categorization`: a ranked list of already categorized transactions that merit a human check. Explain evidence as “worth reviewing,” never as a proven error or probability of error. High rule confidence must not suppress mixed-retailer ambiguity.

- Show date, merchant, amount with currency, current category/subcategory, account, category assignment source and stored confidence, and each review reason. Expand a row for description and transaction details. Offer **Confirm category** and **Change category**, scoped to that transaction. Reuse existing filter parsing and FilterBar, with 50-row pagination that preserves URL filters. No new global filter dimensions.
- Initially flag three transparent signals: **mixed retailer** (Costco/Amazon/Walmart/Target, exact normalized merchant names, category inherited from its merchant rule); **weak mapping** (`fuzzy:` category provenance, `type:` fallback, or non-null category confidence below 0.8); **unusually large** (at least 3× merchant median with five other samples, or 5× category median with ten other samples). These thresholds are proposed defaults, not statistical certainty. Display ratio, median, sample count, and currency for amount flags. Do not infer missing purchases or product identity.
- Use categorized rows only; null/Uncategorized stays in existing Unresolved review. Exclude demonstrably internal flows using the existing loose internal-flow predicate. Do not exclude a row just because its assigned category is Transfers: that assignment itself may need review.
- Exclude category assignments with applied `override:` provenance and every currently matching manual category override or merchant override that explicitly assigns a category, including pending exact and pattern overrides and confirmations that preserve the same category. Match an exact transaction ID first; otherwise evaluate the pattern case-insensitively against the raw description, using the existing engine/impact-helper semantics. Merchant-only overrides do not confirm a category. Multiple independent confirmations/corrections may be saved before re-enrichment; the dirty flag does not disable writes. Other pending automatic rules cannot override an explicit category override. This avoids changing manual override precedence.
- Rank the complete filtered candidate set before pagination: number of distinct reasons descending, then currency, absolute amount descending within currency, date descending, transaction ID ascending. Do not sum different currencies or label rank/confidence as error probability. A large high-confidence Costco merchant-default purchase must appear even without enough history for the amount signal.
- Baselines use other nonzero, categorized, non-internal imported rows in the selected institution/account scope, grouped by currency and direction and either normalized merchant or category. Exclude the candidate itself; skip empty/zero medians and insufficient cohorts. Date/search/category/amount display filters narrow candidates, not their comparison cohorts. Describe this as comparison with other imported transactions, not a forecast. One minimal baseline projection and one filtered candidate query are sufficient; compute sorted cohort medians and rank in the server, then slice. This scans the scoped ledger (roughly O(n log n)); do not claim SQL-bounded pagination or add background jobs/caches.

Assumption: the first version is a local review aid with deliberately conservative, visible rules; confirming a category is a durable manual category choice until removed in Rules. Known previously corrected purchases remain excluded. No new schema is required.

## Current contracts and evidence

- Costco inherits Groceries from its merchant rule (`data/rules/merchants.base.yaml:167`); Amazon, Walmart and Target also have merchant defaults (`data/rules/merchants.base.yaml:471`). The engine gives a direct merchant-derived category confidence 0.9 (`src/ledgerlift/enrich/engine.py:425`), while fuzzy provenance is explicitly prefixed (`src/ledgerlift/enrich/fuzzy_match.py:71`). Stored provenance/confidence fields already exist in both shared DDL and dashboard types (`src/ledgerlift/schema.sql:74`, `apps/dashboard/src/server/data/types.ts:28`).
- Unresolved review selects only absent/Uncategorized categories (`apps/dashboard/src/server/data/queries.ts:432`); filters are validated centrally (`apps/dashboard/src/lib/filters.ts:8`). Review navigation already has its own group (`apps/dashboard/src/components/layout/sidebar.tsx:38`).
- Existing authenticated category-override POST writes rules, not derived transaction rows (`apps/dashboard/src/app/api/rules/category-overrides/route.ts:9`). Upsert conflicts on override ID (`apps/dashboard/src/server/rules/repository.ts:306`); blank dialog IDs derive from merchant/category (`apps/dashboard/src/components/rules/create-rule-dialog.tsx:368`). Synthetic reproduction confirmed two Shopping overrides with ID `shopping` overwrite the first transaction target. New review actions therefore supply `category-review:<complete transaction_id>` explicitly, without slugging/truncation, and reuse that ID on retry. Do not redesign the general rule form.
- Override writes mark enrichment dirty (`apps/dashboard/src/server/rules/repository.ts:325`); the existing banner asks for `ledgerlift enrich --force` (`apps/dashboard/src/components/rules/pending-rerun-banner.tsx:4`). Python applies category overrides before automatic rules (`src/ledgerlift/enrich/engine.py:415`) and persists derived fields during enrichment (`src/ledgerlift/pipeline.py:450`). Parsing preserves unchanged transaction identities and rejects ambiguous replacements affecting overrides (`src/ledgerlift/pipeline.py:222`, existing regression `tests/test_pipeline_safety.py:52`). Preserve these contracts.

## Non-goals, scope candidates and rollback

No automatic recategorization, suggested product-specific category, mass merchant-rule changes, receipt/OCR/AI service, new review-state schema, recurring jobs, savings targets, or source-category contradiction detector. The last needs a shared source taxonomy rather than treating raw source strings as comparable normalized categories.

Existing override ordering can allow an earlier broad manual pattern to beat a later exact category override (`src/ledgerlift/enrich/engine.py:400`, `src/ledgerlift/store.py:1090`); a synthetic reproduction confirmed that result. It is an adjacent policy issue here: applied manual categories and all currently matching manual category overrides, including pending exact/pattern matches, are excluded before review actions are offered. Do not rewrite precedence as part of this feature. Legacy fresh-database YAML override import concerns are also outside this feature; preserving existing SQLite overrides through enrichment is the relevant contract.

Rollback removes the route/navigation and review-specific detector/UI. Saved confirmations remain ordinary category overrides visible/removable in Rules; removing one and re-enriching restores automatic categorization. No migration rollback is needed.

Implementation starts only after approval; changing manual override precedence remains outside scope.
